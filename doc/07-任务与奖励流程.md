# 07 任务与奖励流程

## 1. 全生命周期时序

```
用户(H5)        API/Redis                管理员(Admin)
   │ 领取1,2,3      │                         │
   ├──────────────▶│ Lua原子: 配额/唯一/建任务  │
   │◀──tasks[]─────┤                         │
   │ 复制文案/存图   │                         │
   │ 去平台发布(站外) │                         │
   │ 提交链接+截图   │                         │
   ├──────────────▶│ 去重校验→建凭证→pending   │
   │               │                         │ 审核首发凭证
   │               │◀─────approve(金额)───────┤
   │◀─通知:到账─────┤ 发首发奖励→approved       │
   │               │ (有数据规则→bonus_open)   │
   │ 数据达标,补截图 │                         │
   ├──────────────▶│ 建凭证(round+1)→pending  │ 审核数据凭证
   │               │◀───approve(按档定奖)──────┤
   │◀─通知:到账─────┤ 追加奖励→bonus_open/finished
```

## 2. 状态机与超时

状态定义与流转表见 [03 数据模型 §9](03-数据模型设计.md)。本节补充执行细节：

- **超时过期**：`sc:z:deadline` zset 驱动；读取时惰性判断 + 每 5 分钟兜底扫描（05 §6）。过期动作：status=expired、配额 +1（如有限）、从用户任务 zset 不删（历史可见）。
- **驳回后重交**：状态回到 claimed，deadline 不变（超时照样过期）；每次驳回原因写入任务，H5 顶部红条展示。
- **素材下架的影响**：已领取任务继续走完流程（审核、发奖），只是大厅不再可见、不能新领取。

## 3. 奖励规则引擎

### 3.1 规则结构（素材 frontmatter，见 03 §4）

```yaml
reward:
  first: 3.00                    # 首发通过即发
  stats_rules:                   # 数据档位
    - {metric: views, gte: 1000, reward: 1.00}
    - {metric: views, gte: 5000, reward: 3.00}
    - {metric: likes, gte: 100,  reward: 0.50}
  stack_mode: highest            # highest=命中取最高一条 / all=命中全部叠加
  max_bonus_rounds: 3            # 数据补发轮次上限，0=关闭数据奖励
```

### 3.2 核算函数（Service 层 `RewardService::calcStatsReward($material, $metrics, $round)`）

1. 逐条规则判断 `metrics[metric] >= gte`，收集命中项。
2. `highest`：按 reward 降序取第一条；`all`：全部求和。
3. 结果为 0（无命中）：审核仍可通过，但本笔奖励 0（管理员界面明示「数据未达标，通过但不发奖」），轮次照常 +1。
4. 金额以分（整数）计算，规则编辑界面约束两位小数。

### 3.3 发放入账（与审核同事务语义，Redis 层顺序执行）

```
approve 凭证(sub_id):
  ├─ HSET sub status=approved, reward_amount, reviewer, reviewed_at
  ├─ 核算金额 → INCRBY 用户奖励流水（新建 reward detail）
  ├─ HINCRBY task total_reward / bonus_paid / bonus_round
  ├─ HSET task 状态推进（bonus_open 或 finished）
  ├─ HINCRBY sc:stat:mat:{mid} approve 1
  └─ ZREM sc:z:sub:pending sub_id
```

> 无跨键事务，故顺序固定为「先写凭证结果、再动钱、再动任务」；中断由管理端重试按钮（review 接口幂等：sub 已 approved 直接返回当前状态）。

## 4. 奖励发放（打款）

| 阶段 | 状态 | 说明 |
|------|------|------|
| 入账 | granted | 审核通过即入账，用户端可见累计金额 |
| 打款 | paid | 运营线下/批量转账后在管理端标记；记录 paid_at |

预留字段：`reward.channel`（manual / wx_redpack / alipay / points），本期恒为 manual，接入微信商家转账 API 时只改打款服务，流水与前端不动。

## 5. 审核规范与防刷

### 5.1 审核操作规范（管理员 SOP）

- 首发凭证：核对 ①链接可访问且指向正确平台 ②截图与链接内容一致 ③发布时间晚于领取时间 ④内容与素材相符（带话题等）。
- 数据凭证：核对截图数据 ≥ 用户自报数据（自报仅参考，以截图核定档位）；同轮次截图需能看出是同一条内容的数据页。

### 5.2 防刷措施（本期实现）

| 措施 | 实现 |
|------|------|
| 链接全局唯一 | `sc:dedup:url` hash，写入前 HGETNX 语义（HSET + 判定），命中返回 2005 |
| 截图粗查重 | 文件 md5 → `sc:dedup:img:{md5}`，TTL 30 天 |
| 频率限制 | 领取 ≤20 次/日、提交 ≤10 次/日、登录 ≤5 次/分钟（`sc:rate:*`） |
| 唯一领取 | Lua 原子 + `sc:uq:claim` 唯一标记 |
| 账号封禁 | 管理端可 `status=banned`，封禁用户 token 失效、任务冻结 |

### 5.3 预留（本期不做）

多设备指纹、同内容平台查重（用平台搜索人工抽查）、代理商模式。发现作弊以人工封号 + 拒付处理。

## 6. 通知设计（从简）

本期无推送通道，采用 **H5 内红点 + 短信预留**：
- 任务列表 tab 显示「审核结果」红点（task.reviewed_at > 用户上次查看时间）。
- 预留 `NotifyService` 接口位（log 驱动起步），后续接微信模板消息/短信。

## 7. 异常场景对照表

| 场景 | 系统行为 |
|------|----------|
| 领取时素材刚下架/配额空 | Lua 返回错误，多选整体回滚，提示具体原因 |
| deadline 前最后一刻提交但网络失败 | 以 API 落库时间为准；过期后提交返回 2006 |
| 管理员审核时素材已改规则 | 奖励按**凭证提交时刻**的规则快照核算（凭证创建时冗余当时规则 JSON） |
| 用户提交他人链接 | 人工审核发现 → 驳回；多次 → 封号 |
| 重复点击领取 | `sc:uq:claim` 拦截，返回已有 task_id |
| Redis 数据损坏 | dump 恢复（每日备份），内容库不受影响；状态丢失部分人工对账奖励流水 |
